# 小米 15 Pro 旧版快充移植完整操作手册

适用设备：小米 15 Pro（`haotian`，型号 `2410DPN6CC`）

本次成功版本：`OS4.0.0.19.XOBCNXM`

当前槽位：`_a`

最终有效分区：`vendor_dlkm_a`

> **DTBO 边界：本仓库不提供 DTBO。**
>
> 要恢复完整旧版快充爬升，必须自行使用 `OS3.0.305` 或更早、且与本机和分区匹配的 DTBO。DTBO 与设备版本绑定，不能用其他机型或来源不明的镜像代替。

## 一、先记住成功公式

本次成功不是单纯替换几个 `.ko`，而是下面几件事全部同时成立：

1. 使用当前系统官方 `vendor_dlkm` 作为完整基底。
2. 选择 28 个互相配套的旧版充电 KO，而不是只换 5 个核心模块。
3. 保留旧版 `.text` 功能代码。
4. 只修改 KO 中引用当前系统符号的 CRC，不手工改 `vermagic`。
5. 把 28 个 KO 整个替换进 `.19` 分区，保留其他相机、显示、USB、网络模块。
6. 按原分区参数重建 EROFS、SELinux 标签和 AVB hashtree。
7. 在 `fastbootd` 中写 `vendor_dlkm_a`，不在普通 bootloader 写。
8. 刷入前准备同一系统的官方回刷镜像。

任何一步缺失都可能出现卡第一屏、USB 失效、充电约 10 W、模块加载失败或无法回刷。

## 二、先分清两种任务

### 任务 A：仍然是 OS4.0.0.19，只想重新打包

如果系统版本、模块 ABI 和槽位都没有变化，可以直接复用本目录中的：

- `modules\*.ko`：已经完成旧版代码回移和 `.19` CRC 适配的 28 个 KO。
- `vendor_dlkm_OS4.0.0.19_官方回刷.img`：官方 `.19` 基底和回刷镜像。
- `tools\build_oldcharge19.sh`：本次构建流程参考。

这种情况下不要重新猜模块、不要重新改 CRC，直接按原参数重打包即可。

### 任务 B：以后升级到新的 OS4 版本

换新系统后，不能直接复用当前镜像，也不能假设当前 28 个 KO 原样可用。必须重新：

1. 导出新系统自己的 `vendor_dlkm`。
2. 提取新系统 `/lib/modules` 中的全部 KO。
3. 以当前 `modules\` 目录作为“旧版 `.text` 代码来源”。
4. 重新分析新系统全局导入/导出符号 CRC。
5. 按新系统 CRC 再补丁一次。
6. 以新系统官方分区为基底重建镜像。

当前 28 个 KO 的核心 `.text` 已经是旧版功能代码，所以以后不用再找 `.16` 作者版整镜像；只需要一个新的官方 `vendor_dlkm` 提取目录来提供新 ABI CRC。

## 四、为什么不能只换几个 KO

本次分析结果：

- KO 总数：28
- 导入 CRC 补丁：11
- 导出 CRC 补丁：6

新版系统改变了多个充电模块之间的导出接口 CRC。例如：

| 符号 | 旧值 | `.19` 值 |
| --- | --- | --- |
| `mca_smartchg_if_ops_register` | `0xf068973d` | `0x85e2f9d0` |
| `platform_fg_ic_ops_register` | `0x6a652a09` | `0x870b9e22` |
| `strategy_class_fg_ops_register` | `0x378db201` | `0x944e1834` |
| `platform_fg_ops_qbg_send_chg_data` | `0x7db31002` | `0x1f521b43` |
| `platform_class_buckchg_ops_register` | `0x6fc9751a` | `0x129fc036` |
| `platform_class_cp_register_ops` | `0xce284cad` | `0x901217e7` |

如果只把旧 KO 塞进去，会出现：

```text
Unknown symbol
disagrees about version
module verification failed
```

即使模块表面上加载了，也可能因为策略链不完整导致充电异常。

## 六、CRC 适配原则

### 必须做

1. 解析目标新系统全部 KO 的导入和导出符号。
2. 建立一个全局“符号名 -> 唯一 CRC”映射。
3. 对旧版 KO 的 `__versions` 导入 CRC 做 8 字节小端补丁。
4. 对 `__crc_*` 导出 CRC 做 4 字节小端补丁。
5. 补丁后重新解析 KO，确认每个导入和导出 CRC 都能在新系统中唯一匹配。

### 绝对不要做

- 不要手工重建 KO。
- 不要修改 `.text`。
- 不要改变 KO 文件大小。
- 不要把 `vermagic` 擅自改成 `uname -r` 显示的值。
- 不要在无法唯一确定目标 CRC 时随便选一个值。

本次验证要求：

```text
旧版 .text 哈希不变
补丁前后文件大小相同
除 CRC 字段外不能有其他字节变化
vermagic 必须与目标官方分区中的同名 KO 一致
```

一个容易误判的点：

本次手机 `uname` 可能显示较新的内核构建串，但官方 `.19` `vendor_dlkm` 内 KO 的
`vermagic` 是模块实际加载依据。不要因为 `uname` 字样不同就擅自改 `vermagic`。
应以“目标系统官方同名 KO”的 `modinfo vermagic` 为准。

## 七、同版本重打包流程

以下流程用于仍然使用 `OS4.0.0.19` 的情况。

### 1. 准备目录

```bash
WORK=/tmp/vendor_dlkm_rebuild
rm -rf "$WORK"
mkdir -p "$WORK/baseline" "$WORK/build" "$WORK/verify"
```

### 2. 解包官方镜像两次

`baseline` 用于前后对比，`build` 用于修改。

```bash
fsck.erofs --extract="$WORK/baseline" --preserve \
  vendor_dlkm_OS4.0.0.19_官方回刷.img

fsck.erofs --extract="$WORK/build" --preserve \
  vendor_dlkm_OS4.0.0.19_官方回刷.img
```

### 3. 只替换 28 个 KO

```bash
for f in modules/*.ko; do
  install -m 644 "$f" "$WORK/build/lib/modules/$(basename "$f")"
done
```

不要额外新增第二个 `sc8581.ko`，不要留下英文字母大小写不同或名称重复的副本。

### 4. 重建 EROFS

当前 `.19` 使用这些参数：

```bash
mkfs.erofs \
  -b 4096 \
  -z lz4hc,9 \
  -C 4096 \
  -T 1230768000 \
  --preserve-mtime \
  -U e3611c9c-5568-5aed-97f3-4806df331338 \
  --all-root \
  --file-contexts=file_contexts_vendor_dlkm.txt \
  "$WORK/vendor_dlkm.img" \
  "$WORK/build"
```

`file_contexts_vendor_dlkm.txt` 的关键规则：

```text
/ u:object_r:vendor_file:s0
/.* u:object_r:vendor_file:s0
/etc(/.*)? u:object_r:vendor_configs_file:s0
```

### 5. 添加 AVB hashtree 和 FEC

当前 `.19` 参数：

```bash
python3 avbtool.py add_hashtree_footer \
  --image "$WORK/vendor_dlkm.img" \
  --partition_size 88707072 \
  --partition_name vendor_dlkm \
  --hash_algorithm sha256 \
  --salt a8367d32a09ff6ce8b8687bbb571a7f78a728c72e148bf4d6770c9cce6a1e095 \
  --block_size 4096 \
  --fec_num_roots 2 \
  --algorithm NONE \
  --rollback_index 0 \
  --prop com.android.build.vendor_dlkm.os_version:15 \
  --prop com.android.build.vendor_dlkm.fingerprint:Xiaomi/haotian/haotian:15/AQ3A.250226.002/OS4.0.0.19.XOBCN:user/release-keys
```

这些不是临时参数，必须从官方镜像中读取：

```bash
python3 avbtool.py info_image --image official_vendor_dlkm.img
```

不能删除 AVB footer。本次官方分区大小是 `88,707,072` 字节，原始 EROFS 数据区是
`86,368,256` 字节，剩余空间用于 hashtree 和 FEC。

## 八、换新系统时如何重新做 CRC

### 1. 解包新系统官方镜像

```bash
fsck.erofs --extract=new_stock --preserve new_system_vendor_dlkm.img
```

### 2. 以当前成品模块作为旧代码来源

当前 28 个 `modules\*.ko` 的 `.text` 已确认是旧版。以后不必再追着找 `.16` 作者整包，
只需把它们当作 `source`。

现有 `tools\port_modules.py` 使用的思路：

```text
base        = 旧版功能代码参考
author16    = 已经能在旧版 OS4 加载的旧功能 KO
stock19     = 目标新系统全部官方 KO
output      = 重新适配 ABI 的 28 个 KO
```

以后可以把当前 `modules\` 同时作为旧代码参考和源 KO，把新的官方解包目录作为目标 stock。

### 3. 必须重新验证

```bash
python3 verify_port.py \
  <旧版参考modules_root> \
  <当前旧功能modules_root> \
  <新系统stock_root> \
  <patch输出目录>
```

通过标准只能是：

```text
modules=28 failures=0
```

如果有任何一项失败，不要刷入。

## 十、刷入流程

### 1. 确认手机和槽位

```powershell
adb devices -l
adb shell getprop ro.product.device
adb shell getprop ro.build.version.incremental
adb shell getprop ro.boot.slot_suffix
```

### 2. 进入 fastbootd

```powershell
adb reboot fastboot
fastboot devices
fastboot getvar is-userspace
fastboot getvar current-slot
```

只有 `is-userspace: yes` 才是 `fastbootd`。

### 3. 确认逻辑分区名

本次设备在 fastbootd 中实际可写的是：

```text
vendor_dlkm_a
```

查询：

```powershell
fastboot getvar partition-size:vendor_dlkm_a
```

本次返回：

```text
partition-size:vendor_dlkm_a: 0x5499000
```

`0x5499000` 等于 `88,707,072` 字节。

### 4. 刷入

A 槽位：

```powershell
fastboot flash vendor_dlkm_a "C:\完整路径\vendor_dlkm_米15p_4.0.19.img"
```

B 槽位才使用：

```text
vendor_dlkm_b
```

### 5. 重启

```powershell
fastboot reboot
```

## 十三、已知坑和错误判断

### 坑 1：只改 DTBO 想恢复旧版快充

方案已经验证不够。新版 KO 中的循环降流、云端 FG、SOC 平滑和策略状态仍在，
单独换 DTBO 可能只能开机但充电约 10 W，甚至触发第一屏。

### 坑 2：直接刷 `.16` 作者整分区

会把相机、显示、USB、网络等模块一起带回旧版，风险远高于只替换充电模块。

### 坑 3：只替换 5 个核心 KO

ABI 和依赖不完整。当前方案必须成套替换 28 个 KO。

### 坑 4：按 `uname` 强行改 vermagic

错误。使用目标官方分区中同名 KO 的 vermagic。

### 坑 5：普通 fastboot 模式写 vendor_dlkm

错误。`vendor_dlkm` 是 `super` 动态分区，必须在 `fastbootd` 写当前槽位逻辑分区。

### 坑 6：新增重复 SC8581

不要额外塞一个 `sc8581.ko`。本次使用系统原有文件名 `sc8581_sy6541.ko`，
避免两套 CP 驱动同时存在。

### 坑 7：用电脑 USB 判断快充失败

电脑 USB 通常只有约 3 W。必须接原装高功率充电器并检查真实协议和功率。

### 坑 8：看到 AVB release string 不同就直接判定失败

应检查 `verify_image` 的 footer、hashtree、FEC、salt 和描述符。本次 `avbtool 1.3.0`
生成的 `NONE` footer 已验证通过，手机也能正常启动。

### 坑 9：看到 `strategy_fg_parse_dt failed, ret=-22`

本次开机日志也有这一行，但 FG、Buck、CP 继续工作，系统正常启动。不能只凭一条
parse 日志判定整个方案失败，要结合模块加载、电源节点、实际充电和完整日志判断。

### 坑 10：看到 `Unbalanced IRQ wake disable`

本次该告警来自 Wi-Fi `cnss2` 关闭 PCIe 的调用栈，不涉及充电。应看调用栈，
不要看到一次 WARNING 就把原因归到充电 KO。
