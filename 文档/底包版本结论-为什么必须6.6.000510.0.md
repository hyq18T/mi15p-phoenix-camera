# 底包版本结论：为什么必须用 6.6.000510.0

结论日期：2026-09-28
分析对象：Phoenix 1.3.0 所需底包 `6.6.000510.0` vs 用户提供的 `6.6.000570.5`

## 结论

**必须使用 `6.6.000510.0`。`6.6.000570.5` 不能作为底包使用。**

570.5 不是 510 的"升级版"，而是**另一条构建分支**的产物。Phoenix 1.3.0 的 410 个补丁条目是从 510 的官方解包树逐类抽出来的**整类替换文件**，它们与 510 强绑定，不存在"向下兼容到 570"的可能。

570.5 唯一的用途是：如果将来要基于它重做一版补丁（相当于重走路线 B），它可以作为新的底包候选。

## 输入校验

| 项 | 官方相机-6.6.000510.0 | 参考-官方相机-6.6.000570.5 |
| --- | --- | --- |
| 大小 | 193,895,068 B | 194,121,049 B |
| SHA-256 | `6bf98a86...f47b662` | `2017533862...037875` |
| versionCode | 660005100 | 660005705 |
| META-INF 内嵌 GIT 修订 | `4e0db46eb07e66843d11f38f91860da5f4c0fd78` | `f9be8736991a351da8d804f677fcb6af7e719de8` |

用户提供的两个 APK 与项目内已存文件哈希完全一致：`相机-6.6.000510.0.apk.1` 与 `官方相机-6.6.000510.0-底包.apk` 相同，`相机-6.6.000570.5.apk.1` 与 `参考-官方相机-6.6.000570.5.apk` 相同。

## 证据一：构建器的硬校验

`tools/build_phoenix.py` 的 `build_camera()` 每次构建都计算输入 APK 的 SHA-256，与 `supported-camera.json` 比对，不匹配即抛出 `Unsupported camera APK; see supported-camera.json`。上游 README 明确"仅支持以下底包"，`supported-camera.json` 中也标注 `description: the only supported input APK`。

上游发布说明（V1.3.0）同样写明："基于小米 17 Ultra OS4 官方相机底包的 Phoenix 移植版本，主要面向小米 14 Ultra（`aurora`）"。

## 证据二：两个包不是同一版本的小改

对 510 与 570.5 的 ZIP 条目逐条比对（条目名集合相同，各 6075 个唯一名 / 6199 条）：

| 类别 | 数量 | 说明 |
| --- | --- | --- |
| 内容不同 | **1315** | 含全部 11 个 `classes*.dex`、`resources.arsc`、`AndroidManifest.xml`、`lib/arm64-v8a/libDocumentProcess.so` |
| 仅 510 有 | 2 | `META-INF/services/Ew.q`、`yw.B` |
| 仅 570 有 | 2 | `META-INF/services/Ew.p`、`yw.A` |

`res/*.xml` 中有约 1200 个"大小相同但内容不同"——典型的资源 ID 重新编号现象。两个包来自不同 git 修订，是两次独立构建。

## 证据三：资源 ID 大规模错位

用 `aapt2 dump resources` 提取两版 ID→资源名映射：

| 指标 | 数值 |
| --- | --- |
| 510 资源条目 | 21,647 |
| 570 资源条目 | 21,657 |
| 两版同 ID | 19,652 |
| 其中名称一致 | **12,518（63.7%）** |
| 其中名称不同（ID 错位） | **7,134（36.3%）** |
| 仅 510 有的 ID | 1,995 |
| 仅 570 有的 ID | 2,005 |

再验证构建产物的编号归属（`work/camera.unsigned.apk` 的 `resources.arsc`，22,387 条）：

| 对比 | 同 ID 数 | 名称一致 |
| --- | --- | --- |
| 构建产物 vs 510 | 21,647 | **21,514（99.4%）** |
| 构建产物 vs 570 | 19,723 | 12,385（62.8%） |

即：**Phoenix 的产物使用 510 的资源编号体系**（patch 里的 `res/values/public.xml` 钉死了 510 的 ID 表，22,387 条 `public` 声明）。

代码里有大量硬编码资源 ID（`0x7fxxxxxx`）。若混用版本，指向就会错：

| 场景 | 可解析 ID 数 | 指向不同资源 |
| --- | --- | --- |
| 补丁 smali（510 来源）放进 570 编号表 | 1,180 | **605（51.3%）** |
| 570 底包全部 smali 放进 510 编号表 | 19,854 | **8,700（43.8%）** |

后一行是关键：570 底包里未被补丁覆盖的类会保留 570 自己的 R 常量，而产物 arsc 用的是 510 编号，约 44% 的资源引用会指到错误资源。

## 证据四：逐类比对 410 个补丁条目

用 `06_测试/补丁兼容性实测/compare_510_570.py`，按类描述符在两个官方解包树（各约 34,150 个类）中定位并比对：

| 指标 | 数值 |
| --- | --- |
| 补丁 smali 条目总数 | 410 |
| 类在 510 底包中不存在（Phoenix 新增类） | 13 |
| 类在 570 底包中不存在 | **62** |
| 510 与 570 该类源码完全相同 | **34** |
| 510 与 570 该类源码不同（版本漂移） | **314** |
| 补丁内容与 510 原样相同（空补丁） | 14 |
| **570 自身实现会被 510 代码覆盖** | **307** |

也就是说，用 570 当底包会得到这样一个 APK：507 个类来自 570、约 397 个类被换成 510 的版本（其中 307 个是 570 已有实现的覆盖），另外还有 49 个 510 存在但 570 已删除/改名的类被当作新类塞回去。这是一个版本混血的产物。

570 中缺失的类（节选）：`Lcom/prometheus/camera/backup/SettingsBackupArchive;`、`Lcom/xiaomi/camera/cloudfilter/util/StaticFilterAssets;`、`LF1/B4$b;`、`LG8/n;`、`LE4/p$a;` 等，以及 20 余个混淆类名。

明细见 `06_测试/补丁兼容性实测/patch-vs-510-570.json`。

## 对当前设备状态的影响

15 Pro 上现已安装 `6.6.000570.5`（versionCode 660005705）。这**不影响**Phoenix 的构建与安装：

- Phoenix Camera APK 是一个**完整相机应用**（510 的全部 6199 个条目 + Phoenix 资产），安装时整体替换 `com.android.camera`，与手机原装版本无关。
- Phoenix 的 versionCode 为 **760010300**，高于 660005705，属于升级安装，不需要降级放行。
- 唯一需要匹配的版本是"小米相册-编辑"（`com.miui.mediaeditor`），目前设备上是 `2.4.0.5.2`，Phoenix 要求 `2.4.0.4.3`。

## 补充（2026-09-28）：这条约束究竟约束了什么

先厘清一个最容易误解的点：**"必须用 6.6.000510.0"约束的是构建输入，不是手机上的相机版本。**

Phoenix 的相机产物是一个**完整相机 APK**（510 的 6199 个条目 + Phoenix 新增 593 个），安装时整体替换 `com.android.camera`（产物 versionCode `760010300`）。所以：

- 手机原装相机是 6.4、6.6 还是 6.7，与 Phoenix 产物无关，**不需要降级原装相机**；
- 真正被钉死的只有一件事：拿去**构建**的那份 APK 必须是 510。

换句话说，装了 Phoenix 之后，你用的相机已经不是小米原厂那一版了，它就是 Phoenix 这一版（510 血统 + Phoenix 功能）。所谓"用不了新版的相机"，准确说不是功能被限制，而是**相机替换成了 Phoenix 自带的这一版**。

## 补充：新版底包（6.6.000570.5 / 15 Pro 自带 6.7.000180.0）能不能用

### 15 Pro 自带 6.7.000180.0

`02_数据/15pro-camera-6.7.000180.0-base.apk`（198,788,689 B），从其 `classes*.dex` 字符串表提取 **38,023** 个类描述符，与 410 个补丁条目逐一比对：

| 指标 | 数量 |
| --- | --- |
| 补丁 smali 条目 | 410 |
| 类名在 6.7 底包中存在 | **237（57.8%）** |
| 类名不存在 | **173（42.2%）** |
| 其中类名含非 ASCII（Unicode 混淆名） | 37，**全部缺失** |

对比 6.6.000570.5 的 348/410（84.9%），6.7 的表面命中率更低。但更关键的是：

> **"类名存在"不等于"就是同一个类"。**

- ProGuard / R8 式混淆的短名（`LA3/j;`、`LE4/p$a;`）是按构建顺序**重新分配**的。换一个 git 修订重新构建，同一个名字很可能指向完全不同的实现；
- 37 个 Unicode 混淆名（形如 `L䁋䁇䁅䀆...;`）**必然**每次构建都不同，按名称匹配的命中率恒为 0；
- 因此 237 只能算**乐观上界**，真实可复用比例只会更低。

缺失的 173 个类绝大多数是 MIUI 内部实现类（`LC4/H`、`LE4/u`、`LF1/B4` 等），需要在新底包里按方法/字段签名重新定位并重写补丁。明细见 `06_测试/补丁兼容性实测/missing-in-15pro.txt`。

### 资源 ID 会第三次重排

`0x7fxxxxxx` 形式的硬编码资源 ID 在 410 个补丁条目中出现 **1,638 次，分布在 117 个文件**（补丁 smali 里引用 `Lcom/prometheus/**` 共 169 处）。补丁树的 `res/values/public.xml` 钉死了 510 的 ID 表，产物 `resources.arsc` 与 510 同 ID 的 21,647 条中 21,514 条名称一致（99.4%）。

而 510 与 570 之间同 ID 名称已错位 **36.3%（7,134 条）**；6.7 是第三次重排。换底包后这 1,638 处字面量必须整体重映射，否则会随机指向错误资源，而且**错得静默**。

### 补丁的体量

| 项 | 数值 |
| --- | --- |
| 补丁文件总数 | 1,129（620 新增 + 509 覆盖已有） |
| 覆盖的 smali 类 | 389（改写 MIUI 已有混淆类） |
| 补丁 smali 代码量 | 893,076 行 / 20.9 MB |
| 硬编码资源 ID | 1,638 处 / 117 个文件 |

这不是"打个补丁"，是**整类替换 + 全量资源重打包**。

## 想把 Phoenix 的功能做进新版相机，需要做什么

| 路线 | 做法 | 成本 | 状态 |
| --- | --- | --- | --- |
| **A** | 直接装 Phoenix 整包，替换原装相机 | 已完成 | **今天就在跑**。功能齐全，代价是相机为 510 血统 |
| **B** | 以 6.7 为底包重做补丁 | 大 | 见下方任务清单 |
| **C** | 等上游发布基于新底包的版本 | 0 | 上游 `AI_CONTEXT.md`：适配新底包需"重新建立补丁、类映射、资源与运行验证" |

### 路线 B 的任务清单（供评估）

1. **类重定位**：为 173 个在 6.7 中不存在的类找回对应实现（按方法/字段签名匹配，而非类名）；37 个 Unicode 混淆名只能按行为特征定位。
2. **资源 ID 重映射**：把 1,638 处 `0x7fxxxxxx` 从 510 编号表整体映射到 6.7 编号表，并重建 `public.xml`。
3. **语义漂移核对**：389 个被覆盖的 MIUI 混淆类，逐一核对 6.7 版本的字段/方法签名与调用约定。
4. **资源基线对齐**：补丁新增 521 个 `res`、77 个 `assets`，需与 6.7 的基线重新合并。
5. **真机逐项验证**：上游 `verification.json` 对 1.3.0 都标注 `deviceValidation: not performed`。本项目的经验是**只有真机能定性**——本项目就是靠真机才发现 ODM 逐文件 bind 不存活（见 `06_测试/实机验证/实机验证记录.md` 第 3 节）。

### 建议的前置动作

若要做路线 B，先做一个**可行性 spike**（约 1～2 小时）：不改任何代码，只统计"补丁 smali 引用到的 MIUI 方法/字段签名，在 6.7 底包里还有多少对得上"。这个数字能把"能不能做"从感觉变成定量判断。

## 另一条同样硬的版本绑定：相册编辑器

相机之外，"小米相册-编辑"（`com.miui.mediaeditor`）也有硬绑定，原因完全一样——**LSP 用 `Class.forName` 直接查混淆类名**。本机已实测：`2.4.0.5.2` 上 8 个目标类有 5 个已不存在，滤镜投射链路应视为失效（而文件级资产同步与原生水印渲染不受影响）。详见 `05_文档/相册编辑器版本绑定实测-2.4.0.5.2.md`。
