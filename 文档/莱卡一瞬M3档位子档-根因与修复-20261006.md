# 「莱卡一瞬(M3)」档位子档点不动 —— 根因与修复（2026-10-06）

## 现象

「莱卡一瞬」（M3，mode = `0x100`）里点缩放条 `1x` / `10`，标签不变（不出现 `1.2x/1.5x/20x`），
无法进入子档；拍照模式、超清实况（`0xe7`，上一轮已修）正常。

## 判定链与三处闸门

缩放条点击是否进入子档，由三处共同决定：

1. **缩放条点击白名单**：`Lcom/android/camera/ui/zoom/ZoomRatioToggleView;->onClick` 的 `:cond_22`，
   逐个比较 `this.q`（当前 mode）与 `0xa3/0xa8/0xab/0xe8/0xe7/0x100`，命中后调用
   `Lv2/v0;->isSupportMode(I)Z`。
2. **组件支持判定**：`Lv2/v0;->isSupportMode(I)Z` 对 `0xa3/0xa8/0x100` 走 `:cond_4`，
   末尾统一调用 `LJe/c;->O1(I)Z`。
3. **机型子档位表**：`LJe/c;->O1(I)Z` 的实现是

```
.method public final O1(I)Z
    iget-object p0, p0, LJe/c;->e:L<deviceConfig>;
    invoke-virtual {p0}, L<deviceConfig>;->B1()Ljava/util/Map;
    move-result-object p0
    if-eqz p0, :cond_0
    invoke-static {p1}, Ljava/lang/Integer;->valueOf(I)Ljava/lang/Integer;
    move-result-object p1
    check-cast p0, Ljava/util/HashMap;
    invoke-virtual {p0, p1}, Ljava/util/HashMap;->containsKey(Ljava/lang/Object;)Z
    ...
```

即 **`deviceConfig.B1().containsKey(mode)`**。

机型配置对象来自 `LJe/e;->G0()`：

```
new-instance v1, Ljava/lang/StringBuilder;
-> append("com.mi.device.")
-> append(Je/e.k(LJe/a;->c))          # k() = 首字母大写
-> Ljava/lang/Class;->newInstance()
```

`k()` 实测为「小写化 + 首字母大写」，15 Pro 上 `ro.product.device = haotian` →
类名 `com.mi.device.Haotian`。已用两个反证交叉确认（`0xe7` 修复后只有 `Haotian.B1()` 被改过，
而该修复真机生效）。

## 底包与上游补丁的差距

| 机型类 | `B1()` 是否含 `0xe7` | `B1()` 是否含 `0x100` |
| --- | --- | --- |
| `com.mi.device.Haotian`（15 Pro，运行时） | 否（上一轮已补） | **否 ← 本轮阻塞点** |
| `com.mi.device.Aurora`（14 Ultra） | 否 | 否 |
| `com.mi.device.Nezha`（15 Ultra） | 是 | 是（原生支持 M3） |

`ZoomRatioToggleView:cond_22` 与 `v2/v0.isSupportMode` 的 `0x100` 分支在底包里**本来就有**，
所以唯一缺口就是 `Haotian.B1()` 缺 key `0x100`。

上游 LSP 模块 `M3EntryPoint.installM3QuickFocalConfig()` 用「把 Nezha 的 256 号定义并入
active 机型 B1()」的方式补这一格，但机型写死成 `com.mi.device.Aurora`：

```java
Class<?> activeConfigClass = XposedHelpers.findClass("com.mi.device.Aurora", loader);
XposedHelpers.findAndHookMethod(activeConfigClass, "B1", ...);
```

15 Pro 的运行时机型类是 `Haotian`，该钩子永不触发（这也是「M3 入口能进、子档点不动」同时出现的原因：
入口由 `Je/c.W0()`、`r2.A` 等与机型无关的钩子放行）。

## 修复

在 `smali_classes3/com.mi.device.Haotian.smali` 的 `B1()` 末尾（`return-object p0` 之前）追加：

```smali
    # Phoenix-15Pro: M3(0x100) 复用拍照(0xa3) 的子档位表 [1.0/28mm/35mm , 10/20]
    const/16 v1, 0x100
    invoke-static {v1}, Ljava/lang/Integer;->valueOf(I)Ljava/lang/Integer;
    move-result-object v1
    const/16 v2, 0xa3
    invoke-static {v2}, Ljava/lang/Integer;->valueOf(I)Ljava/lang/Integer;
    move-result-object v2
    invoke-virtual {p0, v2}, Ljava/util/HashMap;->get(Ljava/lang/Object;)Ljava/lang/Object;
    move-result-object v2
    invoke-virtual {p0, v1, v2}, Ljava/util/HashMap;->put(Ljava/lang/Object;Ljava/lang/Object;)Ljava/lang/Object;
```

与上一轮 `0xe7` 完全同构：直接复用拍照（`0xa3`）那张已验证的子档位表，
使 `Je/c.O1(0x100)` 由 `false` 变 `true`。`.locals 7`，v1/v2 复用安全
（v3 承载 `[1.0, 28mm, 35mm]`、v4/v6 为 1/2、v0 为 SparseArray，均在本块之前已消费完毕）。

> 为什么不用 Nezha 的 256 号原生定义：那是 15 Ultra 的口径（主摄 23/28/35 与配套长焦环），
> 用户要的是「和默认相机一样」（1x→1.2→1.5、10→20），且 0xa3 通路已实机验证；风险更低。

## 验证

见 `06_测试/莱卡一瞬档位子档-20261006/记录.md`：1x→1.2x→1.5x→1x、10→10x→20x、
20x 出图、退出后拍照模式无回归，全部真机通过。
