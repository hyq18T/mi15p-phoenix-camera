## Bug 3：实况运镜（红毯运镜）卡死 / 闪退 —— 已修复

### 现象

模式栏选到「实况运镜」（模块 id `0xe7` = 231），预设红毯运镜，进入即卡顿并反复重启相机会话。

### 证据链

模式入口的判定链：

```text
MasterLiveModuleEntry.support()  ->  Je/c.e.y4()      // y4() = 本机是否为支持运镜的机型
```

15 Pro 上原生返回 `false`。本次日志（`Q0Fix` 标签）直接记录了改写过程：

```text
[Q0Fix][Y4] #N Chagall_gl.y4() = false -> true（运镜开关）
[Q0Fix][Y4] #N Common.y4()     = false -> true（运镜开关）
[Q0Fix][Y4] #N Xuanyuan.y4()   = false -> true（运镜开关）
[Q0Fix] 目标包=com.android.camera 进程=com.android.camera 变体=V4-CORE 设备类=8 开关[y4=true sup=true zoom=true devcfg=false probe=true]
[Q0Fix][SUP] 已挂 MasterLiveModuleEntry.support()Z
```

进入后底层直接失败：

```text
09-29 03:13:40.014  onModeSelected from 0xa3 to 0xe7
09-29 03:13:40.016  enterNewMode: newModule=MasterLiveModule mid = 231
09-29 03:13:44.485  E MCAM_CameraDeviceCallbackImpl: onCameraError: other error 0x101
09-29 03:13:44.485  E MCAM_BaseModule: onCameraException: mid = 231, cid: 2
CamX: [ERROR][CSL] camxcslhw.cpp:2965 CSLSubmitHW() Error Submitting device, DeviceIndex: 7
CamX: [ERROR][NCS] camxncsintfqsee.cpp:2484 FillCap() Sensor 6 probe failed during boot
```

`0x101` = `ERROR_CAMERA_DEVICE`。之后每 2.1 秒重试一次 `0xe7 -> 0xe7`，循环到 03:14:39 才退出。

### 根因

15 Pro 只有 3 个后置（主 / 超广 / 长焦），不具备「实况运镜」所需的相机设备组合；底包是 17 Ultra 的相机，其模式入口本来靠机型判定挡住。`PhoenixQ0Fix` 把这个判定强制打开，等于在 15 Pro 上放出一个硬件不支持的模式。App 侧无法修复底层 HAL，只能关闭入口。

### 修复

两处 smali（`01_源码/15Pro适配补丁-Bug修复-20260929/`），均在 `Build.DEVICE == "haotian"` 时短路：

| 文件 | 改动 |
| --- | --- |
| `lsp/smali_classes11/com/nezha/q0fix/PhoenixQ0Fix$1.smali` | `y4()` 的 `afterHookedMethod` 直接 `return-void`，不再把 `false` 改成 `true` |
| `lsp/smali_classes11/com/nezha/q0fix/PhoenixQ0Fix$2.smali` | `support()` 的 `afterHookedMethod` 强制 `setResult(Boolean.FALSE)` |

两处必须同时改，否则会被另一处重新抬回 `true`。结果：15 Pro 上「实况运镜」入口按原生行为隐藏。其他机型不受影响。

验证：新 LSP 的 `classes11.dex` 中出现 `haotian` 字面量，旧版没有；SHA-256 见交付目录。

## Bug 1：夜景 + 徕卡经典 → 纯绿照片 —— 已缩小范围，待对照复现

### 样本

`06_測試/Bug复现-20260929/绿片样本/`：`IMG_20260929_031304/031305/031307.jpg`（03:13，三张全绿）+ 回收站找回的 `IMG_20260929_025436.jpg`（绿）与 `IMG_20260929_025444.jpg`（正常）。

全部为 3072×4096、`mjpeg`、`yuvj420p`。

### 已排除：LUT 文件损坏

`/data/vendor/camera/lut_cvstyle_common.png`（124,501 B，mtime 等于拍摄时刻）是**合法 PNG**，解码后是标准的 8×8 块、每块 64×64 的 `64³` 3D LUT，且接近恒等（对角线 `(63,63,0) → (254,255,58)`）。可视化见 `06_测试/Bug复现-20260929/lut对比/设备-lut_cvstyle_common-可视化.png`。

顺带查清了官方底包的 LUT 存放方式：APK 内 `res/raw/lut_cvstyle_*.png` 里 **20 个有 18 个不是 PNG 头**（只有 `lut_cvstyle_bixi_common/night` 是明文），而 `lut_normal_*.png` 全是明文 PNG。也就是说官方对 cvstyle 系列 LUT 做了加密，运行时解密后写到 `/data/vendor/camera/`。加密体 124,517 B 与解密体 124,501 B 正好差 16 字节（IV 前缀），与实测一致。

结论：设备上那份 LUT 内容正确，**绿片不是 LUT 文件被写坏**。

### 关键新证据：主图纯绿，但内嵌辅图是真实画面

对 `IMG_20260929_031304.jpg` 做缩放采样统计：

```text

```

即整幅主图没有任何画面结构，只有一层平滑暗角（中心亮、四角暗）。

但同一文件里有 3 段 JPEG 流（SOI 偏移 `0` / `1975` / `358543`）：

| --- | --- | --- |

尾部那张灰度图里能清楚看到显示器、桌面、窗帘 —— 说明**画面实际采到了，是最终渲染输出被替换成了纯绿**。四张照片（含正常片）都带这张 1536×2048 灰度辅图，属该相机的常规结构，不是异常。

## Bug 2：「超清」下 EV 面板空白 —— 待复现

### 澄清：「超清」不是独立模式

底包中文资源 `work/camera-base/res/values-zh-rCN/strings.xml`：

```xml
<string name="frp">超清生效模式：拍照、专业</string>
<string name="fsx">超清</string>
<string name="g3t">超清</string>
<string name="g3j">人像超清</string>
```

所以「超清」是**拍照 / 专业模式里的一个开关**，不是一个模式项。用户描述应为：在拍照（或专业）模式打开「超清」后，EV 调节项在，但点开面板是空的。

### 已有线索

LSP 侧与 EV 相关的注入点是 `CameraV51Bridge.installNightControls()`：

- `NightModule.supportEvOverlap()` 被 `XC_MethodReplacement.returnConstant(true)` 无条件改成 `true`；
- `registerNightEvProtocol / unregisterNightEvProtocol` 反射调用 `Xg()` 取对象后再调 `E(obj) / r(obj)`。

这些目前只作用于 `NightModule`，而「超清」在拍照 / 专业下走的是另一条模块链路，因此**不能直接断定这条就是原因**，需要实测日志。

## 三、852113 是怎么来的（已定位到具体代码）

`l6.b.d(int scene)` 是相机 App 自己的「经典」效果映射（`work/camera-base/smali/l6.1/b.1.smali:174`）：

```smali
.method public static d(I)I
    const/16 v1, 0xd
    ; scene 0 / 其它 → 0x91，scene 3 → 0x92，scene 0x19 → 0x93，
    ; scene 9,0xa,0xd,e → 0x94，默认(packed-switch 0x10..0x12) → 0x95，scene 6 → 0x96
    const/16 p0, 0x91
    invoke-static {v1, p0}, Li3/b;->c(II)I
```

`i3.b.c(a,b)` 就是 `(a << 16) | b`（`work/camera-base/smali/i3.1/b.smali:336`）：

```smali
.method public static c(II)I
    shl-int/lit8 p0, p0, 0x10
    or-int/2addr p0, p1
```

所以 `d(0)` = `(0xd << 16) | 0x91` = **852113**，与日志 `target=852113` 完全吻合。
而日志里的 `previous/native = 852992` = `(0xd << 16) | 0x400`，低 16 位是 `0x400` 而不是过滤表里的 `0x91..0x96` ——
说明 LSP 拿来比较的「native」和它写回去的「mapped」**根本不在同一个取值空间**，因此每轮比较都判为「不一致」，于是每轮都强写 852113。

写回动作在 `CameraV51Bridge.syncClassicCvState`（`work/lsp/smali/com/prometheus/camera/rev/CameraV51Bridge.smali`）：

```
.line 1855   v6  = EffectController.s().i()        ; native 当前效果
.line 1851   v14 = l6.b.d(scene)                   ; 经典映射
             if-eq v6, v14, :cond_5                ; 相等 → 跳过写回
.line 1870   if-nez v9, :cond_5                    ; aiEnabled != 0 → 跳过写回
.line 1874   EffectController.Y( mapped )          ; 强写经典效果 id
```

这个强写就是夜景 + 经典的触发源；不写（`cvType=0`，即徕卡生动）时 `renderType=0`，出片正常。

## 七、Bug 2 定论与修复（2026-09-29 06:11，LSP 第五版）

### 7.1 现象坐实

用户录屏 `8ea739c7dce0dd3ef8b49a9c40b65130.mp4` 抽帧（`99_临时\ev-video-20260929\`）与 adb 亲自复现一致：
更多模式弹窗 → 超清 → 点左下 EV → 底栏整排隐藏约 1 秒后回来，**面板内无任何控件**。

### 7.2 根因（推翻上一节"菜单项 id 错配"的猜测）

面板控件数量不取决于菜单项 id，而取决于 EV 组件的数据列表：

1. EV 面板 Fragment `LP4/t;`（tag `MCAM_FragmentManuallyExtra`）的数据源是 `Lr2/D0;`。
   `Lr2/D0;` = `ComponentManuallyEV` —— 本底包里**同时**含 `isSupportMode(I)Z` 与
   `pref_camera_manually_exposure_value_abbr` 的类只有它（`Lv2/d0;` 只有 `isSupportMode`）。
2. `r2.1/D0.smali:1889-1944`（`v(IILj9/e;)`）：

   ```smali
   invoke-virtual {p0, p1}, Lr2/D0;->isSupportMode(I)Z
   move-result p1
   if-eqz p1, :cond_2
       … invoke-virtual {p0, p1}, Lr2/D0;->s(Lj9/e;)Ljava/util/ArrayList;  # 真正填选项
   :cond_2
   invoke-static {p2}, Ljava/util/Collections;->unmodifiableList / iput mItems
   ```

   `isSupportMode == false` ⇒ `mItems` = **空列表** ⇒ 面板渲染成空白。
   `s(Lj9/e;)`（`r2.1/D0.smali:1670`）只读 HAL capabilities（`r()` + `Lj9/f;->t/u`），**没有第二道设备配置闸门**。
3. `isSupportMode(I)Z` = `y(I) || x(I)`（`r2.1/D0.smali:1314`）；`y(173)`/`y(175)` 均 false；
   `x(175) = Z1() || D4()`、`x(173) = Z1()`（`r2.1/D0.smali:207-315`）。
4. `Z1()` = `Je/c;->e`（设备配置对象）的 `Q6() && R6()`，而 `Q6()/R6()/D4()` 全形如
   `instance-of p0, p0, L<设备配置子类>;` —— **能力位完全由运行时选中哪个设备配置类决定**。
   `Je/e;->G0()` 按设备代号反射 `com.mi.device.<Codename>`；本底包（小米 17 Ultra OS4 相机 6.6.000510.0）
   只带 8 个设备配置（`Q0Fix` 探针实测：Common / Chagall_gl / Warhol_gl / Xuanyuan / Byron / Athens / Songyuan / Nezha），
   haotian 不在其中 → 落到不支持该能力的配置 → 173/175 一律 false。

**结论：这是"移植包设备配置不匹配"造成的，不是官方相机的问题（15 Pro 官方相机超清/夜景下 EV 可用）。**

### 7.3 修复（只动 LSP，不重建相机 APK）

新增 `lsp/smali/com/prometheus/camera/rev/CameraV51Bridge$71.smali`（同时实现 `InstallStep` 与 `XC_MethodHook`），
并在 `CameraV51Bridge.install()` 末尾挂上一步：

- `run()`：`Class.forName("r2.D0", true, loader)` + `XposedHelpers.findAndHookMethod(clazz, "isSupportMode", Integer.TYPE, this)`；
- `afterHookedMethod()`：读 `args[0]`（mode）；仅当 mode ∈ {173, 175} 时打印原值，
  若原值为 `false` 则 `param.setResult(Boolean.TRUE)`；日志限流 20 条。

用 `afterHookedMethod` 而非 `beforeHookedMethod`，为的是**一条日志同时给出"原值"与"强制生效"**，便于判定根因。
不采用 DEVCFG 整体替换（上游标注"未启用，只观测"，会连带影响所有读 DEVCFG 的模式与控件）。

补丁包：`01_源码\15Pro适配补丁-EV面板修复-20260929\`（含 `apply.ps1`，带改前/改后哈希守卫）。

## 10. Bug 3（实况运镜 / 红毯运镜）最终收口 —— 移除红毯预设（2026-09-29 晚）

真机在场（ADB 直连 `dc16f1e0`），不再走 LSP hook 路线，改为**直接改相机 APK 的 smali**。

### 10.1 为什么放弃 HAL 侧「修好红毯」

红毯运镜需要 `com.xiaomi.sessionparams.enableMasterLivePhoto` vendor tag + HSR/慢动作能力。
15 Pro 的 HAL 没有该 tag（设备日志：`lookupTag: Tag name 'enableMasterLivePhoto' does not exist`），
`MasterLiveModule` 每 ~2 秒重建会话，表现为卡顿 / 面板点不动 / 闪退。
HAL 侧补 tag 不可行（需要在 vendor 相机 provider 里新增 tag 定义），因此改为**摘掉这个预设**。

### 10.2 为什么放弃 LSP hook 路线（重要纠错）

前几轮在 LSP 侧尝试 hook `v2.d0.getItems()` / `getDefaultValue(I)` / `getComponentValue(I)` 来过滤红毯：

- `installStep` 的 `run()` 成功执行（`PhoenixML: hooked …` 三条日志确实出现），
  `Class.forName("v2.d0")` 与 `findAndHookMethod` 都没有抛异常；
- 但 `afterHookedMethod` 始终没有产生可观测证据；
- 更严重的是**实验代码本身有逻辑错误**：`getComponentValue` 的探针写成
  「结果**不等于** `"1"` 就强制改成 `"2"`」，等于把所有人（包括超清实况）都改成主角运镜。

处置：**已从构建沙箱回滚**——`CameraV51Bridge.smali` 恢复为 `8689AE9D…83B413`（与"EV 面板修复"后的既定状态一致），
删除 `CameraV51Bridge$72..$78.smali`；重建出的 LSP 与已验证第五版 **11 个 dex 哈希完全一致**，且不含 `PhoenixML` 标记。
`01_源码/15Pro适配补丁-实况运镜预设修复-20260929/lsp/` 仅作留档，`lsp/apply.ps1` 不再使用。

### 10.3 最终方案：从 item 列表里摘掉红毯

关键事实（本轮静态确认 + 真机验证）：

| 判据 | 证据 |
| --- | --- |
| 预设按钮**只**来自 `v2/d0.getItems()` | 适配器 `Lr9/a.<init>(Context, Lcom/android/camera/data/data/c;)` 构造时取 `component.getItems()`；点击 `R4/b.gr(…)` 也按该 list 索引取 `d.q` / `d.k` |
| 按钮文案随 item 走 | 每个 item 的 `d.k` = `master_live_panel_*` 资源，item 没了按钮和文案一起没 |
| `R4/b.Zq()` 是死代码 | 全树无任何 `LR4/b;->Zq` 引用（上一轮「标签+item 必须同步删」的结论**不成立**） |
| `pref_master_live_key` 只有 `v2/d0` 读写 | 全树 3 处命中（`getKey` / `getComponentValue` / `setComponentValue`） |
| 预设映射 | `q="0"`→ultra_pixel（超清实况）、`q="1"`→slow_motion（红毯）、`q="2"`→non_linear（主角）、`q="3"`→linear（自由） |

改动（单个文件 `smali/v2.1/d0.1.smali`，三处）：

1. `initItems()` 的 `:pswitch_6`（`q="1"` 分支）末尾 `add` → `nop`；
2. `getDefaultValue(I)` 的 `q()` 空集兜底 `"1"` → `"0"`；
3. `getComponentValue(I)` 读完 pref 后把 `"1"` 归一为 `"0"`（`.locals 2` → `.locals 3`）。

补丁目录：`01_源码/15Pro适配补丁-实况运镜预设修复-20260929/apk/`（含 `apply.ps1` 与产物哈希守卫）。
