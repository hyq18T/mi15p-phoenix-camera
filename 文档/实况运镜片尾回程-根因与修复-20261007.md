# 实况运镜「片尾回程丢失」根因与修复（2026-10-07）

- 设备：Xiaomi 15 Pro `2410DPN6CC` / `haotian` / `dc16f1e0`
- 装机：相机 `Phoenix-1.3.0`（底包 6.6.000510.0）+ LSP 模块
- 成片：自由运镜亮场 `175 帧 / 8.007 s`；主角运镜亮场 `192 帧 / 8.002 s`

---

## 一、现象

用户拍「实况运镜」（主角运镜 / 自由运镜）时，取景框里镜头**先放大、后缩小**（回程），
但回放内嵌视频时，回程阶段「冻住一瞬，然后直接闪跳回最小倍率」，没有平滑动画。

## 二、根因链（完整）

内嵌视频（MVIMG 里的 mp4）长度由**编码器切片窗口**决定，窗口两端为：

```
tail = g + (captureDuration − head_{g→now})
```

- `g` = 快门时刻（`ym.k.g`）
- `ym.e.d`（= `captureDuration`，构造参数 `args[3]`）= 切片**上限**
- `ym.e.e`（= `preCaptureDuration`，`args[4]`）= 预录长度，实况运镜为 1,500,000 µs

实况运镜的原生 `captureDuration` 只有 **3,040,000 µs**，而去程动画本身就要 3.0 s（自由运镜 `zoomSpeed 3.0`，
主角运镜 2.0 s + 停留），**回程被挤到窗口之外** → 视频在回程前就封帧 → 观感即「冻住后闪跳」。

放大到 8,000,000 µs 后，窗口尾部到达 `g + 4.81 s`（暗场）／更早（亮场），
足以覆盖回程结束点（`g + 3.42 s`），回程随即进入视频。

### 2.1 为什么不能无条件改

普通「动态照片」和实况运镜**共用同一条编码链**，`ym.e` 构造实参完全相同
（cap 3,040,000 / pre 1,500,000 / `args[2]=true` / `args[8]=false`），
**唯一区别只有 MediaFormat 的 height**（普通 1440 / 自由运镜 1920），用分辨率做门控不稳妥。

### 2.2 采用的门控

新增钩子 `$6`（钩 `xm.c.d(Lxm/b;)Lym/d;`），在方法入口用反射读取 `xm.b` 的三个 public boolean
`l` / `m` / `n`（由 `xm/k.run()` 在 `getModuleIndex()==0xe7` 即 231 时按 `pref_master_live_key` 赋值），
映射为静态字段：

| 字段 | 含义 | `pref_master_live_key` |
| --- | --- | --- |
| `mlMode=1` | `l` = 红毯运镜 | `1` |
| `mlMode=2` | `m` = 主角运镜 | `2` |
| `mlMode=3` | `n` = 自由运镜 | `3` |
| `mlMode=0` | 无（含普通动态照片、超清实况） | `0` |

同时写入 `mlStamp = System.currentTimeMillis()`。`$5`（钩 `ym.e` 9 参构造）只在
**`mlMode ∈ {2,3}` 且 `now − mlStamp < 2000 ms`** 时把 `args[3]` 由 3,040,000 改写为 8,000,000。

> 说明：反射读取（`XposedHelpers.getBooleanField`）是必需的——直接 `check-cast Lxm/b;` 会因
> 模块类加载器解析不到应用类而抛 `NoClassDefFoundError: Failed resolution of: Lxm/b;`。

## 三、本轮踩到并修掉的坑（重要）

`$5` 的时间窗判断写成了 `if-gez v13, :doPatch`。smali 的 `if-gez` 语义是
**「vA ≥ 0 时跳转」**，而我们想要的是「差值 < 2000 µs 时补丁」。
`cmp-long` 结果在差值小于阈值时为 −1，`−1 ≥ 0` 为假 → **永不补丁**。
由于 `$6` 与 `$5` 同一毫秒执行（差值恒为 0），该 bug 表现稳定复现。

修正：`if-gez` → **`if-ltz`**（vA < 0 时跳转），修复后日志由 `cap=3040000 ml=3` 变为 `cap=8000000 ml=3`。

## 四、字段与常量速查

| 名称 | 值 |
| --- | --- |
| `ym.k.e / f / g / t` | head / tail / 快门 / 硬上限 |
| `ym.e.d` = captureDuration | `args[3]`，3,040,000 → 8,000,000（门控） |
| `ym.e.e` = preCaptureDuration | `args[4]` = 1,500,000 |
| cap 常量 | `l`=0x5cc600(6.08 s)、`m`=0x200b20(2.1 s)、`n`=0x2e6300(3.04 s)、`k`=0x26c1e0(2.54 s) |
| 窗口公式（`$1`） | `need = (src + \|(\|tgt−src\|−1)\|×0.0375 + 0.3 + 0.32) × 1e6` |
| 自由运镜 | `zoomSpeed 3.0`，4.2→8.4，`arm us = 3,720,000` |
| 主角运镜 | `arm us ≈ 2,682,500`（实测） |

## 六、与《实况运镜片尾-落点更正-20261007》的关系（更正）

前一份文档结论为「`ym/k.f` 不是视频长度来源，回程永远在窗口之外，按原设计做不到」。
本轮实测证明该结论**不成立**：

- 视频长度由 `ym.e.d`（captureDuration）决定，不是由 `ym.k.f` 决定 —— 这一点旧文说对了；
- 但**窗口一旦足够长，回程就会进入视频** —— 旧文的「永远在窗口之外」是错的（它是在 cap 仍为 3.04 s 的前提下得出的）。
- 因此不需要「提前回程触发」，只需把 `captureDuration` 拉长到覆盖回程即可。
